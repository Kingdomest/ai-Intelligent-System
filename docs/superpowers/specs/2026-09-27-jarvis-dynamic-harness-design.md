## 1. 用户目标与已确认边界

保留现有 TypeScript、Node.js、Fastify、React、SQLite 和 Ollama 技术栈，参考本地 `D:/project/codex-main` 的架构重构贾维斯，不直接接入 Codex app-server，不整体迁移 Rust。

主智能体根据任务创建、配置并调度子智能体，不再依赖固定的“实施／测试／评估”角色列表。每个子智能体是独立会话，有自己的上下文、状态和执行循环；职责配置动态生成，执行内核统一。测试和评估依旧是系统必须满足的关卡，但承担这些职责的角色由主智能体按需创建。

自进化必须留下经过验证、下次能实际检索和使用的工具、经验、角色模板及回归用例；源码问题必须进入已有的受控修复流程，不能只解释错误或保存“下次注意”。这不是模型权重训练，也不是允许模型无审批修改运行中的系统。

继续保留以下用户确认的要求：

- 文件／目录未指定位置时默认当前项目目录；用户明确指定的路径不能被默认位置覆盖。
- 基础动作优先使用内置且经过测试的通用工具，未知能力由子智能体生成；同类任务的目标作为参数，不能写死首次需求。
- 沿用请求批准、帮我批准、完全访问三种权限模式。权限决定由现有代理执行，动态角色不能自行提升权限。
- 整个用户任务共享最多五个完整纠正回合，不按模型调用、文件、工具或子任务分别给五次额度。
- 子智能体执行、测试、评估完成后，错误证据返回主智能体和原执行者，原执行者能够继续改进。
- 生成工具缺陷由主智能体根据证据决定是否重建；有问题的版本退出可复用状态，保留历史记录供审计和回退。
- 沙箱契约通过不等于本机功能通过；需要真实效果的任务必须有相应证据，无法验证时不得报告成功。
- 用户明确要求源码修复才进入源码修复工作流；正式补丁应用与服务重启分别需要明确批准，完全访问模式也不豁免。无可验证的 OS 隔离时，模型修改过的候选代码动态测试仍需单独测试批准。

成功定义不是“创建了更多 Agent”，而是角色确实按任务变化、失败反馈能驱动改进、重复任务能复用已验证成果、恢复不重复副作用，并且成功报告有可检查的证据。不能承诺所有未来需求或环境变化永不出错；可以对已知缺陷建立可执行的防回归保障。

## 5. 核心结构化契约

### 5.1 AgentSpec

每个 Spec 含角色显示名称、职责描述、目标、所负责的 taskNodeId、必要输入和 artifactRefs、允许能力、申请的权限范围、输出契约 ID、验收条件、资源预算、可选模板来源，以及 requestedModelProfileId、reasoningProfile、nativeReasoningRequest 和简短 selectionReason。角色名和职责不是固定角色枚举；推理策略是受控配置枚举，不是角色白名单。

内核生成 agentId、parentAgentId 和 rootTaskId；不接受模型伪造身份。输出契约从内核管理的产出类型选择，例如文本、工具候选、测试计划、核验结论、上下文摘要、经验候选、源码补丁候选，不接受任意可执行 schema。结构化字段有长度与数量上限，超限在创建会话前拒绝。

模型生成的职责属于任务级配置，优先级低于系统规则。工具输出、附件、经验正文和其他 Agent 消息均是带来源的数据，不能覆盖系统权限或验收策略。

第一版仅主智能体可以创建子智能体；子智能体若需要新职责，向主智能体提出结构化请求，不能自行递归组队。模板是可调整的参考，不是固定角色名单，也不携带未来任务的授权。

### 5.2 AgentSession、消息与产出

AgentSession 保存不可变身份关系、Spec 版本、任务图绑定、会话状态、历史游标、上下文摘要版本、当前轮／步骤、结果引用和错误证据引用，以及模型申请、resolvedModelConfig、配置／能力版本和调整原因。状态包括 queued、running、waiting、paused、completed、failed、cancelled；等待原因区分依赖、审批、用户信息、资源和子会话结果。

AgentMessage 含 messageId、发送／接收会话、父任务、纠正 roundId、类型、脱敏内容／证据引用和 deliveryMode。queue_only 只入箱；trigger_turn 安排已有会话继续执行。消息去重、游标、状态和唤醒意图事务性保存；持久化待处理消息是事实来源，内存事件仅用于唤醒。不会把“接受消息”冒充“Agent 已阅读并执行”。

TaskArtifact 含产出类型、生产会话、任务图／输入版本、来源、哈希、创建时间和访问范围。原文件或大结果放在受控本地存储，事件只保存引用和脱敏摘要。完成通知去重，不反复启动主会话；终态产出也能供后续明确的 follow-up 引用。

### 5.3 运行决策与模型适配

主会话可提出调度、继续已有子会话、读取状态、等待结果、调用已授权工具、请求信息、安排核验、提出纠正路线、提出源码修复或完成候选。子会话只能提出其职责和工具范围内的动作、产出或信息请求；不能批准自身操作、直接注册 active 工具、写正式源码或绕过主智能体创建新 Agent。

每个模型回合输出有界的结构化 action，内核先校验，再执行；一回合不能塞入无界的操作脚本。Ollama 可以继续使用 JSON 输出实现 action envelope，未来原生 tool calls 也映射到相同契约，不强制模型支持 Codex 的 Responses API。

调度动作、读状态和模型续答不单独算一次纠正，但都消耗步数、时间与推理预算。无效 action 的反馈改进使用任务共享纠正额度；不能在网关内部偷偷重复五次，然后在外层再重复五次。

### 5.4 模型、推理策略与角色配置解析

创建子智能体是在创建执行会话，不是在创建／训练新模型。每个会话独立保存上下文和状态，但可以共用同一个 Ollama 推理服务；不要求每个会话各自加载一份 27B 权重。共享模型也不等于独立核验一定正确，验证规则仍由第 7 节决定。

#### 模型清单与选择

ModelRegistry 的每个配置项包含稳定 profileId、providerId、模型标识、启用状态、版本，以及已核验的上下文／输出容量、结构化输出支持、原生 thinking／effort 选项和资源约束。原生能力区分 supported、unsupported、unknown，并保存确认来源；不从模型名称含有“qwen”“reasoning”等字样推断支持情况。

连接地址、认证和其他秘密由服务端配置管理，主智能体只看到 profileId 及脱敏能力描述。主智能体不能直接提交任意 baseUrl、密钥、模型安装命令或未登记的模型名称。只有用户配置并启用的模型可供选择，不因已有 OpenAI 兼容适配器就自动增加收费／远程模型。

兼容现有配置：默认把当前 MODEL_MODE／MODEL_NAME 映射为 `local-default` 配置项。当清单只有一个可用模型时，未指定模型的所有子会话使用该模型；主会话也使用用户配置的默认项。以后用户明确添加其他模型时，主智能体可按任务要求和资源约束选择，但新选择仍通过统一解析与调度。

当前模型不可用时，返回具体模型不可用原因；不自动下载、切换未登记模型或转到外部服务。若要改用另一已登记模型，主智能体必须提出可检查的配置变更，明确记录变更原因；用户明确指定的模型不得被静默替换。

#### 推理策略与原生推理设置分离

reasoningProfile 是 `lightweight`（轻量）、`standard`（标准）或 `deep`（深入）的任务处理策略，用于选择有界上下文／输出预算和工作方式，不代表后端已开启某个原生 effort。

| 策略 | 适用工作示例 | 首版总上下文窗口申请上限 | 单次输出申请上限 |
| --- | --- | --- | --- |
| lightweight | 明确的分类、简短提取、格式整理 | 8,000 token | 2,048 token |
| standard | 通常的任务执行、文档整理、产出核验 | 16,000 token | 4,096 token |
| deep | 根因分析、复杂计划、工具方案或源码补丁评审 | 32,000 token | 4,096 token |

上下文窗口包含系统提示、职责、历史、工具信息和输出保留空间，仍适用第 9、14 节的最小输出预留、容量核验和共享预算。以上是申请上限，不保证模型支持，也不为 deep 额外发放步骤、纠正回合或更长的两分钟请求超时。temperature 首版默认零；它和输出长度都不被当作原生推理强度。

nativeReasoningRequest 为 `auto` 或模型配置中已明确列出的选项 ID。选项 ID 由适配器映射到真实接口支持的参数，例如经核验的 thinking 开关或 effort 级别；系统不把统一的 high 字符串直接发给所有 Provider。未支持或未核验的显式选项，在推理请求发送前拒绝，返回 NATIVE_REASONING_UNSUPPORTED 或 NATIVE_REASONING_UNVERIFIED，不伪装成功启用。

auto 只采用该配置项已经核验的默认设置，不推断“deep 就必须打开 thinking”。为兼容当前正式代码，`local-default` 的初始推理申请保持关闭；须核验该部署对关闭参数的支持，不把代码里已经发送 `think: false` 当作 Provider 已确认执行。启用其他原生选项必须先有该部署的能力记录。auto 且能力未知时不下发未经核验的可选原生参数，返回默认行为未确认的状态及原因；它不等于已经确认关闭。API／UI 明确标注原生推理未确认；逻辑策略可以运行，但不能宣称原生低／中／高已经生效。若任务／用户明确要求某个原生功能（包括强制关闭）而能力未知，则阻塞，不用逻辑预算冒充满足要求。

#### 配置优先级与角色提示

解析顺序：系统硬限制与当前用户授权先约束可行范围；在范围内按“用户对当前任务的明确指定 → 主智能体 AgentSpec 显式申请 → 已验证模板建议 → 用户配置的子会话默认 → 当前有效主会话配置”选取值。用户仅要求“深入分析”是任务策略请求，不擅自解释为其已指定某个 Provider 原生 high 选项。没有明确配置的子会话默认 standard；不从主会话偶然的 deep 设置无提示地继承高消耗策略。

模型和原生选项分别解析，然后做组合校验；选择模型 A 不能继承模型 B 的推理参数。角色模板不能覆盖用户明确选择，能力限制和任务剩余预算也不能被模板／AgentSpec 放宽。主智能体的预算申请可被收紧并记录原因；用户硬性要求无法满足时给出冲突原因，不静默降级后声称已满足。

角色提示由固定系统规则、动态职责、当前任务目标／必要约束及输出契约组合；附件、工具输出和经验正文以有来源的数据块提供，不与系统规则混写。角色可以自由定义，但身份、权限、产出契约和模型解析由内核决定。例如同一 `local-default` 模型可以分别创建“文档整理”和“事实核验”会话，使用不同职责、工具范围和上下文，而不创建固定类或另一个模型。

#### 生效快照、运行变更与可观察性

resolvedModelConfig 包含 profileId／providerId、配置的模型标识、逻辑策略、已解析的原生参数、上下文／输出预算、temperature、超时、配置与能力版本，以及被收紧／拒绝的原因。与 requestedModelConfig 一同保存，任务角色详情展示两者，密钥和连接秘密不入快照。

“已解析”表示内核选定配置，“已下发”表示适配器发出了对应参数；只有后端回执或该部署的可复现能力验证能支持“已确认”，三者不得混为一谈。Provider 返回的实际模型标识单独记录；与配置不一致且不属于已核验别名时停止接受该结果并报告 MODEL_IDENTITY_MISMATCH。不保存模型内部推理全文，仅保存脱敏配置、用量和证据摘要。

创建与恢复使用版本化配置快照，不因修改默认配置就偷偷改变正在运行会话。每次模型请求都携带会话生效配置，不能因共享 Provider 而读到另一个会话的模型／推理参数。换模型或策略需在回合边界由主智能体提出、重新解析并记录新版本；用户明确配置和许可仍生效，共享纠正账本及已执行操作不重置。已生成产出保留原配置来源，新的核验不能冒用另一版本的模型配置。

配置更重不意味着可以并发更多请求。ResourceScheduler 对所有配置项共享全局容量，必要时序列化不同模型请求；没有硬件和模型能力证据时，不自动提高默认推理并发。

## 6. 主智能体组队与任务执行

1. Intake 关联同一会话的用户需求、附件、已有失败任务与操作摘要；先检查预算并检索可用工具和有效经验。
2. 主智能体提出有版本的任务图和 AgentSpec，说明必要产出、依赖、所有权、验收条件和是否涉及真实宿主效果。简单问题可直接进入回答核验，不强制创建无用角色。
3. 内核拒绝循环依赖、未知依赖、缺少输入、无界角色、重复所有权和越权配置。用户指定路径、格式与验收要求不能被模型擅自降级。
4. 主智能体通过 AgentController 创建会话；调度器只启动依赖满足且取得资源许可的工作。不同只读工作可以并行；同一文件／目标的冲突写入按资源锁序列化。模型请求限额覆盖主会话、执行、核验和上下文整理，不能为特殊角色绕过全局限制。
5. 子会话运行自己的工具循环。已验证工具优先复用，未知能力先生成候选再经过契约、通用性、测试与评估；通过后仅按能力生命周期进入可用状态。
6. 子任务产出入库后通知主会话。主智能体可调整未完成部分的角色、输入或依赖；改变上游输入时，受影响下游产出失效。已完成的真实操作不会因为任务图改版自动再执行。
7. 必要产出到齐后，经独立核验和最终回答核验，主智能体提出完成；内核重新计算完成条件，通过才落下 COMPLETED 并返回结果。

例如市场分析 PPT 可动态组建资料研究、内容整理、演示制作与成果核验角色；本地文件总结则只需要相应读取／整理与核验工作。角色描述可以变化，工具及产出契约仍统一。

## 7. 验收与权限是内核规则

需要验收的执行产出由不同于生产者的会话核验。主智能体安排承担测试／评估职责的动态 Spec，内核验证身份不同、输出契约正确和证据完整；主智能体没有安排时，完成请求被拒绝并告知缺少的核验，不用隐藏的固定 Agent 替代其调度。

独立会话并不意味着独立模型或自动保证判断正确；同一 Ollama 模型也可承担不同角色。因此固定断言、真实日志和产物检查依旧是事实依据。

TestPlan 仅含数据和受限断言，默认每套最多十个用例，不含模型生成的 JS／Shell／PowerShell 脚本。测试判读不能覆盖执行器的 failed／blocked。测试报告与评估绑定具体产出、工具版本、输入版本和当前验收条件；代码或输入改变后旧通过结论不能复用。

能力路径维持：纯计算能力经沙箱与评估通过可启用；声明宿主权限的能力先 Canary，在真实任务通过效果测试及评估后才 Active。声明权限与实际可访问接口必须一致，不能通过少报权限绕过真实验证。复用失败先区分测试夹具／输入问题与工具缺陷；仅有证据的工具缺陷触发隔离和新版本构建，内置工具缺陷走源码修复而非任意生成工具替换。

迁移仅将缺少本设计要求的版本绑定验证记录的历史宿主 Active 能力降为 Canary，并保存迁移标记；重复启动不把已通过新版真实验证的 Active 再次降级。现有产出一旦与当前输入／代码版本不匹配，不得沿用历史通过报告。

权限范围取当前任务政策、用户授权范围与 AgentSpec 请求范围的交集。用户点击允许只批准被展示的具体操作；拒绝无本机执行。审批与操作日志绑定 rootTaskId、agentId、taskNodeId、工具版本和参数哈希。并行请求进入持久化待审批队列，前端可逐项处理；拒绝影响其依赖任务，不误杀无关只读工作。

应用启动需要目标应用的进程和所要求的窗口／前台证据；看不到桌面或应用身份不明确时阻塞。创建文件／PPT 需要目标路径及实际产物校验；读取总结需要读取结果引用和回答事实核验。干运行、模型自称完成或另一个目标的成功不能代替这些证据。

## 8. 五个完整纠正回合与错误分类

首次执行不计入纠正额度；首次失败后最多五个纠正回合。每个回合是主智能体分配或调整 → 原执行者改进 → 测试 → 评估的一整条链，整个 rootTaskId 共享，不按子任务、工具或 Agent 独立计算。

纠正采用持久化 roundId 和 dispatch／implement／test／evaluate 阶段。回合结束只记账一次；同一回合中的不同失败可以合并为证据，不能让并行子任务各自开启一套五次循环。发生在某个关口的不可执行错误记录为该回合失败／阻塞，不伪造后续阶段已执行。审批等待、补充信息和中断恢复不重置账本，也不因恢复重复扣同一回合。

错误反馈包含阶段、错误代码、原输入引用、实际结果引用、失败断言、工具和产出版本、已发生操作及重放判定。默认 follow-up 原执行会话，保留其有效上下文；职责确实不合适时主智能体可更换角色，但共享账本不变。

主智能体选择以下路线，内核检查其前提：

- plan_or_input：修正计划、依赖或参数，沿用没有缺陷证据的工具。
- generated_tool：停用有缺陷版本，生成参数化新版本并重新走发布测试；旧代码和证据不物理删除。
- answer：已有有效执行成果时只纠正回答，不重放宿主操作。
- source_defect：记录诊断及修复建议；用户明确要求源码修复后进入受控 RepairJob。
- environment／permission／missing_input：说明缺失条件并等待用户，不反复改代码。
- unsafe_or_unknown：结果不确定、重放可能重复副作用或无法取得必要证据时 BLOCKED。

续接同一个未解决任务的“继续／修正”沿用其共享账本；新建子会话或新的请求行不能隐式增加额度。确属新的独立用户任务可有自己的账本。用户明确发起源码修复是独立、可追溯的 RepairJob，沿用已有最多五轮修复设计，不给原任务增加隐形纠正额度。耗尽后显示最后原因、每轮改进摘要、已有成果和未完成部分。

## 9. 上下文交接与安全压缩

子会话默认接收最小 ContextPackage：当前任务目标、约束、职责、必需来源引用、依赖产出、已发生操作和有关失败证据。不默认复制完整聊天或所有附件。

预算计算覆盖系统提示、角色配置、工具定义、历史、来源内容及输出保留量。优先使用实际模型用量和配置；无法精确分词时使用明确标注的保守估算，不能把固定“字符数除四”当所有语言和模型的准确计数。无法确定模型容量时不扩大默认窗口。

在容量耗尽前留出整理预算，主智能体创建上下文整理和独立核验会话。整理提出一种或少量有界方案：来源索引替代全文、已完成步骤摘要、去重或必要片段重取。原始资料保留，摘要必须有来源索引。

权限决定、操作日志、纠正账本、用户约束和验收状态是结构化事实，不由模型自由重写。核验检查关键事实、来源覆盖和摘要预算；通过后以原子方式切换摘要版本，失败保留旧上下文。原上下文也已无法容纳时停止额外推理并报告预算阻塞，不能无限调用更多压缩 Agent。来源重新读取仍经过原权限与数据访问规则。

压缩不会声称保留全部语义；缺失内容可从原始来源重新检索，最终回答需要的证据不能仅靠摘要猜测。

## 10. 自进化与复用

### 10.1 EvolutionRecord

统一记录 kind（经验／角色模板／回归用例索引）、版本、状态、归一化故障／任务类别、来源任务、根因证据、适用条件、工具／项目／模型／环境版本、验证引用、禁用条件、使用信号与失效原因。工具源码继续归 CapabilityRegistry 管理，EvolutionRecord 只引用具体版本。

状态至少包括 candidate、verified、quarantined、superseded。成功次数不自动把候选变成 verified；没有证据的总结不能作为可信经验。

### 10.2 形成与验证

有新问题或有效改进时，主智能体安排动态角色形成候选，另一会话检查来源和适用条件；固定执行器验证可执行部分。相同故障／成果指纹去重，重复经验归并，而非每次任务重新生成工具。

工具通用性至少使用两个不同目标验证，另测缺失输入、边界输入和宿主失败。不得为了验证通用性自动在用户桌面创建额外文件或重复启动应用；宿主测试继承权限，或在获批的受控目标上进行。真实权限能力没有当前必要证据时保持 Canary。

行为经验如步骤选择、参数映射和错误规避规则，必须有结构化前提及通过的任务／回归证据；下一次使用前检查前提。自由文本解释可保留为线索，但不执行、不作为系统指令。角色模板只保存职责和建议输出契约，去除首次目标、用户私有内容和授权。

生成工具的回归用例采用受限 TestPlan；涉及项目源码的回归代码属于 RepairJob 候选，沿用候选测试审批，不把经验整理当作偷偷运行测试脚本的通道。

### 10.3 检索与停用

任务开始时按同类目标、能力 key、故障指纹与环境匹配检索，优先选择 verified 且前提成立的结果。第一版使用 SQLite 结构化过滤和有界文本匹配，不为本次目标新增向量数据库。

检索最多返回少量摘要及证据引用，正文按需读取，不把整个经验库塞进上下文。命中理由可解释，正文依旧按不可信数据处理。工具／环境改变、实际复用失败或适用条件不符时重新验证或停用；既有通过不代表永久可信。记录使用和失败信号，但不凭模型自评分激活。

### 10.4 终态后的整理边界

任务过程中产生的改进优先在该任务的验证链中沉淀。终态后每个任务快照最多安排一次有界整理，通过持久化指纹和租约防止重复；只整理已有证据，不自动重放本机动作、不修改源码、不展开新的五轮纠正。整理失败保留 candidate／原因，不偷偷激活。

经验整理的状态独立于用户任务结果：用户任务已完成而经验待验证时，UI 明确区分，不能声称自进化已经完成。待整理工作在正常运行及恢复时处理，不另外安装计划任务或无界后台服务。

## 11. 源码自更新接入

动态角色替代修复流程中的固定模型职责，不替代固定审批、测试执行器和部署器。主智能体可创建诊断、补丁、复现核验和评审角色，其产出仍符合已有 RepairJob 契约。

普通失败可以记录源码缺陷建议，不能自动启动正式源码修改。用户明确要求修复自身源码后，才进入：失败复现 → 候选补丁 → 基线红／候选绿 → 相关与全量测试、类型检查、构建 → 补丁审批 → 暂存 → 重启审批 → 监督部署／健康 → 原需求真实复验。

沿用 `2026-09-24-jarvis-self-source-repair-design.md` 的本地同会话访问、候选／正式哈希、逐次审批、快照、回退、监督进程和禁止不安全重放边界。审批拒绝、代码变化、服务未被监督或真实复验失败时不得标为 REPAIRED。候选动态测试缺少 OS 隔离时必须另行批准；换目录不是 OS 沙箱。

此次重构本身的代码实施和部署由后续单独批准的实施计划确定；本设计批准不自动批准此前候选正式应用或任何服务重启。

## 12. 存储、恢复与 API

增量保留 tasks、task_events、capabilities、operation_journal；核验并迁移候选 repair_jobs 和会话关联，不删除已有数据。必要新增 agent_sessions、agent_messages、task_artifacts、evolution_records；纠正账本与任务运行版本继续绑定根任务。迁移可重复执行，有 schemaVersion 与兼容测试。

任务绑定 engineVersion，旧未完成任务继续原路径或明确阻塞等待用户，不转换到新内核后重放。新任务启用新内核；已经执行过宿主动作的任务不得失败后静默回退到旧循环再跑一遍。旧终态任务和事件可继续查询。

恢复遵循持久化检查点、消息游标和操作日志，先核对 executing／unknown，再安排未执行工作。成功的纯计算产出及有效只读结果可按输入和证据版本复用；不确定副作用阻塞并请求方向，不声称“恰好执行一次”。重复点击批准、重复消息、服务重启及并行回调都不得重复执行已记录操作。

继续使用当前任务创建、查询、补充信息与审批 API；新增动态会话与进化摘要作为有版本的响应字段，并支持按游标读取 Agent 状态／事件。前端旧 pendingPermission 字段兼容展示队列首项，新增队列接口处理其他请求，不能丢弃并发审批。新增取消入口传播取消信号并释放资源；已发生副作用不会因取消而自动撤销。

没有账户认证时，本地会话令牌／同源校验是本地访问边界，不声称已具备多用户身份隔离。Agent、产出、经验、审批和父任务引用都检查会话／工作区范围，不能仅凭任意 ID 读取敏感资料。

任务事件新增 agent.created／status／completed、correction、verification 和 evolution 摘要；使用统一脱敏 allowlist。事件不保存附件全文、密钥、模型内部推理或完整命令输出。大资料走产出存储与引用，在应用层防止 `.env` 等秘密进入经验库；保留和清理策略不在失败路径删除唯一证据或回退副本。

## 13. 聊天界面

保持现有简约聊天和文件上传，在任务消息下展示可折叠的角色进度：职责、负责步骤、等待原因、测试状态和结果。不是固定的“实施 Agent 已完成”标签。

显示共享纠正回合、主要失败原因及每轮简短改进摘要；显示每个待审批的具体操作与执行者，沿用三种权限模式。终态报告区分 COMPLETED、FAILED、BLOCKED 和 CANCELLED，并显示真实测试通过／失败／阻塞数量。

进化摘要区分“复用已有工具／经验”“新成果已验证”“候选待验证”和“建议源码修复未部署”。历史刷新后从持久化状态恢复，不靠当前浏览器内存冒充结果。审批正文展示必要目标和参数，公开事件保持脱敏。

每个角色的可折叠详情增加模型配置项、模型标识、轻量／标准／深入策略、申请／已解析／已下发／已确认状态及预算调整原因。不支持的原生推理选项不能显示成“高强度已开启”；共享同一模型的不同会话也明确区分。此处是配置可观察性，不增加收费服务接入或模型自动安装界面。

## 14. 运行限额与停止条件

初始安全默认值：全局并发模型请求为一；每个任务同时活跃子会话最多四个，子会话总创建数最多十二个，主会话不计入该角色数但计入模型请求容量。资源限额可在配置中调低；提高推理并发前必须核验当前模型和本机负载，不能因 CPU 核数多就假定 27B 模型可同时推理。

沿用现有五次纠正和五十步，统计所有角色及测试／压缩请求；默认任务主动执行预算十分钟，单次模型请求超时两分钟。主动执行时钟是整个任务有执行活动的墙钟时间，不把并行角色时间重复相加；等待审批、用户输入与事件而无执行活动时暂停该时钟。步数按已提交的结构化 action 计数，格式错误也记一次，单个 action 最多提交一个工具或调度请求；多宿主调用的受控工具另受有界操作预算限制，不能借工具内部循环规避额度。预算上限早于五轮耗尽时可以明确阻塞，五轮是最大纠正额度而非保证一定运行五轮。

上下文容量以经配置／模型核验的较小值为准；未知时默认不超过现有的 32,000 token 预算，输出预留不少于 4,000 token 且不少于生效单次输出上限，并在输入预算使用达到 80% 时安排整理。无法容纳整理及核验也不强行继续推理。

首版结构化硬上限如下，由 schema 和执行器同时检查，不能仅靠提示要求模型自觉限制：

- AgentSpec 角色名 80 字符，职责与目标各 2,000 字符；单次创建请求最多四份 Spec，权限最多五类、能力引用最多二十项、来源引用最多二十项。
- 模型 profileId 与原生选项 ID 各最多 80 字符，只能引用服务端清单；selectionReason 最多 500 字符。主智能体看不到认证字段，也不能在职责文本中绕过模型清单。
- 任务图最多二十个节点，每节点依赖最多二十项；验收条件最多二十条、每条 500 字符；模型不得通过细分节点绕过五十步及十二个子会话的总限额。
- Agent 消息正文最多 8,000 字符，每次加载最多二十条；超过正文上限的大结果改存产出引用，每次仅加载预算内片段，不按长度无提示截断关键事实。
- 每会话摘要最多 8,000 字符，每次整理最多提出三种方案；EvolutionRecord 摘要最多 2,000 字符、适用条件最多十条，每次检索最多五条。
- TestPlan 每套最多十例；一次受控工具调用最多二十次宿主桥操作，超限在下一次本机操作发生前停止并记录已发生操作。归并／终态整理每个快照最多三次模型请求，无自动纠正循环；租约五分钟，执行期间每三十秒续约，失去租约的执行者不能提交晋升。

所有文本长度和 token 限额同时生效，以更严格者为准。配置可收紧上述上限；放宽必须显式修改经过测试的系统配置，不由模型或经验正文决定。

等待事件期间不发无意义模型请求。主会话等待子任务时释放推理槽，不持有资源等待需要同一资源的子会话，避免死锁。无进展、资源不足、预算耗尽或依赖缺证据均给出明确原因并退出／等待；不创建更多角色来规避限额。

## 15. 验收矩阵

| 范围 | 必须验证的行为 |
| --- | --- |
| 动态组队 | 不同任务产生不同职责配置；没有固定角色白名单；子会话越权配置及递归创建被拒绝 |
| 模型选择 | 单模型正常继承；已登记多模型按会话路由；未知／禁用／不可用模型拒绝；不下载、不擅自切外部服务；返回模型身份不匹配不接受结果 |
| 推理配置 | 逻辑策略与原生设置分离；支持／不支持／未知覆盖；显式 unsupported 拒绝；auto 不假装 high；预算收紧、用户硬要求冲突和配置优先级有测试 |
| 配置隔离恢复 | 主／子会话共享 Provider 时参数不串扰；requested／resolved／submitted／confirmed 有明确区分；恢复保留版本；改默认配置不改变运行中会话；策略变更不重置重试或操作记录 |
| 独立循环 | 子会话能工具调用、接收结果、等待与继续；follow-up 保留有效上下文，不重建一套固定调用链 |
| 调度 | 主／子／核验／压缩共享模型容量；同目标写入不竞态；排队、取消、额度释放和等待无死锁 |
| 纠正 | 一个完整链算一个回合；并行失败共享额度；恢复、重新分配、续接请求不重置；耗尽有具体总结 |
| 通用工具 | 两个不同目标、缺失／边界输入、宿主失败；复用失败能正确归因、隔离与重建，无缺陷工具不误删 |
| 权限 | 三模式遵循现有策略；拒绝不执行；子会话不升权；并发审批、重复批准与输入变化都有测试 |
| 真实验收 | dry-run 不激活错误宿主能力；桌面观察缺失阻塞；PPT 真 OOXML、指定路径和内容匹配；总结可追溯读取内容 |
| 上下文 | 大附件不完整复制；关键约束／操作事实保留；摘要核验失败不提交；来源可取回；超预算有界停止 |
| 经验 | 第二次同类请求真实命中并使用成果；不同目标仍适用；过期条件拒用；伪造经验与附件指令不提权 |
| 防回归 | 原缺陷可复现、修复后通过；错误变体可检出；未经验证候选不晋升；整理去重且无额外宿主重放 |
| 源码修复 | 候选流程经重新核验；测试／补丁／重启分别审批；哈希变化失效；监督恢复／回退及原需求复验 |
| 迁移恢复 | 旧数据库迁移幂等，旧任务仍可查询；旧检查点不转新路径重放；持久化消息和 unknown 操作正确恢复 |
| API／UI | 动态角色、等待原因、审批队列、纠正摘要和进化状态可刷新恢复；事件及证据脱敏 |

自动验收包括契约／单元、模型适配、SQLite 集成、Harness 行为、权限与恢复、API、前端测试，以及全量测试、类型检查和构建。结构化假模型用于确定性失败注入，不证明本地模型质量。

真实验收单独记录：当前 Ollama 的动态组队／纠正／复用链及按会话配置的请求；已声明支持的原生推理选项在当前部署上的适配验收；受控目录中的两个不同文件目标和真实 PPT；在获批的受控应用上核验进程与窗口；审批拒绝零操作；重启恢复不重复副作用。没有第二个用户配置模型时，多模型真实运行列为未验收而非自动下载；原生推理无法确认时标注未确认，不宣传为已经生效。真实环境不可用或尚未批准时列为未验收，不用 Mock／沙箱结果替代。

## 16. 设计审阅与下一步

本文把已确认的三部分对话设计落成同一组契约，尚不是实施计划。用户批准本文后，才能编写分阶段实施计划、具体文件及上述 schema 限额的落点、测试命令、候选迁移核验和执行方式。实施计划仍需用户审阅并选择执行方式；正式部署与服务重启保留单独批准，不在文档阶段进行。
