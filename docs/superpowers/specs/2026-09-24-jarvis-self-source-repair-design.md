# 贾维斯源码自修复与失败任务复验设计

状态：用户已批准设计；隔离候选版已实现并通过测试，正式服务应用与重启仍待分别批准。日期：2026-09-24。

## 1. 用户目标与成功定义

用户允许任务首次执行失败，但在明确要求贾维斯“修复系统/修正自身源码”后，贾维斯必须根据失败证据实际修改项目源码、执行测试、部署修复并验证原需求，不能只解释原因、重试同一错误动作，或把“补丁已生成”“构建通过”冒充“问题已解决”。普通任务失败本身**不**自动授权源码修改。

每一次候选源码补丁的应用，以及每一次服务重启，均需要用户单独明确批准；聊天中的“完全访问”也不豁免这两项审批。审批拒绝后不得修改正式源码或重启。对本次部署预先说明并取得批准的自动回退，是同一部署决定的一部分；未获此批准时不能假定可自动回退。修复全过程继承现有任务权限与操作日志约束，不能以自修复为借口重放不可重入的宿主副作用。

只有以下证据全部成立，才能报告 `REPAIRED`：失败可复现；补丁在独立候选副本中使复现用例从失败变为通过；固定的全量测试、类型检查、构建通过；用户批准补丁与重启；运行中的新版本通过健康检查；原失败请求在真实宿主路径上完成并通过验收。受控目录中的等价请求只能证明功能恢复，不能替代用户指定的桌面目标；如用户尚未批准原目标操作，则终态为等待授权而非 `REPAIRED`。若原请求已有不安全副作用，最后一项必须等待用户决定如何继续，不能伪造成功。其他终态必须准确说明卡在哪个关口。

## 2. 已观测的故障，不做猜测归因

- PPT 请求在规划阶段失败：`steps[1].input.content` 期望字符串却收到对象；没有真实本机操作。规划结构校验发生在现有 `unwrapTypedValues` 归一化之前，而且 `filesystem.write_text` 无法生成可用的二进制 `.pptx`。
- 后续两个“为什么还没解决”的任务，数据库操作日志均为零，却被告知“已执行的宿主操作不能安全重放”。回答纠正路径硬编码 `safeToReplay: false`，把无操作任务误判成不安全。
- 前端新消息只上传当前 `message`，没有关联上一失败任务。缺少任务上下文时，系统不能可靠判断“这个问题”指什么，更不能用臆测回答冒充诊断。
- 当前 Ollama 规划器把“内容随意”错误地追问为缺少 PPT 主题。用户已把内容选择权交给系统，这不是必需用户信息。

上述问题至少涉及规划契约、真实文件产物、任务关联、重试判定和源码部署，不能靠把对象强制转成字符串或再调用一次模型解决。

## 3. 方案比较与选择

1. **直接在运行进程中改源码并重启**：实现快，但此项目没有 Git 元数据，无法保证快照、回退和补丁审批之间的状态不变；开发模式的 `tsx watch` 还可能在用户批准重启前自动生效。不采用。
2. **受控候选副本 + 独立修复执行器 + 受监督部署**：模型只提出结构化补丁，固定执行器在副本中验证；用户看过差异后分别批准补丁和重启，保留旧版本以回退。复杂度较高，但可审计、可恢复，采用此方案。
3. **把故障交给外部编码服务或只让用户手动重启**：减少本系统实现工作，但不满足“贾维斯自己修正源码并执行验证”的目标。不采用。

本设计拆成两个有依赖关系的交付增量：先把本次 PPT/规划/追问故障做成可复现验收并修好；再把“明确请求源码修复”建设为可复用工作流。第二增量不能拿第一增量的手工修复冒充自修复能力。

## 4. 任务识别、证据与修复边界

API 增加可选 `parentTaskId`，前端在同一聊天中把最新任务 ID 作为后续请求的父任务。服务端只接受同一本地会话可见的任务引用；当前系统没有登录身份，因此这里不能声称已有跨用户身份隔离。源码修复入口还需限制在本机访问，校验同源请求和会话令牌，不能仅凭任意任务 ID 发起补丁。任务表持久化父任务引用，历史任务默认无父任务。规划 Agent 收到结构化的、脱敏的父任务摘要：原请求、状态、错误代码、测试结论、已完成步骤、操作日志状态和已验证结果引用；不把附件全文、密钥、完整命令输出或模型推理持久化到事件。若用户问“为什么失败”，先据此只读解释；若明确要求“修复系统源码”，进入修复工作流，不当作普通回答纠正。

修复分类先区分计划/输入、生成工具、内置代码、运行环境与权限。只有确定性复现指向项目实现缺陷，才允许创建源码补丁候选；任务缺少信息、模型一次性规划错误、权限拒绝、外部服务失效，均不能凭一句模型判断就编辑源码。即使是计划错误，若同类请求反复失败且能由项目提示、校验或控制流缺陷复现，也可归因为源码缺陷。主 Agent 记录可检查的归因证据，评估 Agent 可否决，但不能覆盖固定测试的失败。

源码补丁只允许落在明确的项目文件清单中，包括 `src/`、`web/src/`、`tests/` 和经单独标注的依赖清单；拒绝触及 `.env`、`data/`、用户桌面、密钥、系统目录、修复快照和审批记录。权限、策略、依赖安装或服务启动代码属于高风险补丁，UI 必须明确标出受影响文件和风险。模型输出是补丁数据，不是可直接执行的 PowerShell、Shell 或任意测试脚本。

## 5. 修复工作流与状态

新增持久化 `RepairJob`，关联原失败任务和发起修复的用户任务，保存状态、候选版本、批准记录、固定命令的测试摘要、基线与补丁文件哈希、部署与回退结果。状态依次为 `DIAGNOSING` → `REPRODUCING` → `PATCH_PROPOSED` → `CANDIDATE_TESTING` → `AWAITING_PATCH_APPROVAL` → `STAGED` → `AWAITING_RESTART_APPROVAL` → `DEPLOYING` → `SMOKE_TESTING` → `REVALIDATING` → `REPAIRED`。无法复现、测试失败、审批拒绝、部署失败、健康检查失败或原任务不能安全复验，进入带具体原因的 `BLOCKED`/`FAILED`/`ROLLED_BACK`，不能报告 `REPAIRED`。

1. 主 Agent 从失败任务和当前源码版本收集证据，形成一个最小复现。复现测试须在未打补丁的基线上失败，且失败点与用户症状一致；无法复现时停止并报告缺失证据。
2. 实施 Agent 在项目外的候选副本中生成受限补丁及回归用例。候选副本有文件清单和哈希，正式项目文件保持不变。每一轮以“诊断/补丁 → 固定测试 → 测试 Agent 判读 → 评估 Agent 结论”为完整单位，修复任务共享最多 5 轮，不按文件、Agent 调用或测试命令单独计数。基础设施中断保留当前轮，不无限开启免费回合。
3. 固定测试执行器运行预定义命令：复现用例、相关单元/集成测试、全量 `npm test -- --run`、`npm run typecheck`、`npm run build`，设置超时、输出上限和资源限额。它不执行模型写入的任意命令，且基线测试副本不能被候选补丁修改来伪造通过。测试 Agent 只能审阅结构化证据，不能把退出码非零改判为通过。
4. 候选源码即使位于副本中，执行测试仍可能触及宿主。优先使用可验证的 OS 级隔离；若当前 Windows 环境没有该能力，候选动态测试必须另行向用户说明风险并取得批准。这项测试批准与正式补丁应用批准、服务重启批准是三个不同决定，界面不得混淆。仅更换工作目录或设置 `NODE_ENV=test` 不能声称为沙箱。未经批准的候选只能做静态检查，不能在本机运行模型修改过的代码。
5. 候选通过后，UI 展示修改文件、差异摘要、复现前后结果、全量测试结果、权限/启动脚本变更和回退计划。用户批准**补丁应用**后，部署器先保存正式文件快照与哈希，再逐文件验证目标仍属于项目并应用补丁；并发变化导致哈希不匹配时停止，不覆盖用户新改动。拒绝则候选保留为未部署记录，不修改正式源码。
6. 服务由独立监督进程管理，正式运行使用构建产物而非自动热重载的开发模式。补丁应用不自动重启；UI 再请求**重启批准**。若当前服务不在监督模式，进入 `BLOCKED` 并说明需要先迁移运行方式，不擅自杀掉现有服务。重启获批后监督进程切到候选版本，检查 API 健康、SQLite 迁移兼容与基本任务读取；失败时按部署审批中明示的回退授权恢复旧快照并重启旧版，记录结果。
7. 新版健康通过后，执行原任务复验。先查看原任务操作日志：零宿主操作的 PPT 案例可在相同权限设置下重新规划；已验证的只读结果优先复用；未知状态或非幂等写入/启动不自动重放，需用户另行决定。复验必须经过真实执行、测试 Agent 与评估 Agent，得到可检查的产物/效果后才标 `REPAIRED`。

## 6. 本次 PPT 故障的通用修复

新增固定、可复用的 `presentation.create` 能力，输入为目标 `.pptx` 路径和有界的结构化幻灯片数据，不把幻灯片对象塞进 `filesystem.write_text.content`，也不让模型运行 Office/PowerShell 脚本生成文件。规划器对“PPT/演示文稿”选择此能力；“内容随意”表示允许系统选择一个默认主题和示例内容，不追问必需主题。需要用户提供的信息只限无法从请求或默认规则确定的目标位置、约束或敏感资源。

可信宿主渲染器把结构化输入生成真实 PowerPoint Open XML 文件，沿用 `filesystem.write` 权限、目标路径检查、审批与操作日志。写入采用临时文件加原子替换或明确的非覆盖策略，避免半成品；不允许以纯文本扩展名伪造 `.pptx`。测试执行器校验实际文件存在、ZIP/OOXML 结构与幻灯片数量/标题，必要时由独立解析器读取；干运行只证明接口契约，不能冒充本机产物验收。工具按目标路径参数化，第二个不同主题与文件名也必须通过，不能写死首次请求。

规划器收到模型的带类型包装值时，在最终 Zod 校验前做受限归一化；不把任意对象强制转字符串。真正的字段类型不匹配应反馈给规划 Agent 改能力或参数，且在任何宿主操作前完成。回答纠正的 `safeToReplay` 从操作日志计算：零宿主操作不应提示“已执行操作不能重放”；有已验证结果时优先只改回答；缺少证据时要回到计划/执行阶段，而不是无限重写无依据的回答。

## 7. 安全、恢复与审计边界

- 修复触发必须是用户明确请求；普通失败只报告并保留可关联的诊断。聊天中的工具输出、附件和失败消息都是不可信数据，不能提升为系统指令或绕过修复审批。
- 候选补丁、测试执行、正式补丁和重启各自有明确状态；补丁批准与重启批准不可合并为一个默认授权。审批记录与被批准补丁哈希绑定，补丁变化后旧批准失效。
- 源码快照及旧构建保留到新版本健康检查与原任务复验结束；清理策略单独处理，不在失败路径删除唯一可回退副本。当前工作目录没有 Git 元数据，因此不能假定可用 `git reset` 回退，也不自动初始化 Git。
- 修复流水线自身失败不得递归启动另一个无界修复任务。故障、五轮耗尽、隔离环境缺失、冲突或不安全重放均须给用户可操作的准确阻塞原因。
- SQLite 持久化状态转换与审批、部署、回退事件；事件仅存哈希、错误码和脱敏摘要，不存完整补丁、附件、密钥或命令输出。候选补丁和快照单独存于受控路径，并限定访问。

## 8. 验收标准

1. 原 PPT 请求在旧版稳定复现规划类型错误；修复后用当前 Ollama 规划“内容随意、放到桌面”不再追问主题，也不把幻灯片对象传给文本写入能力。用两个不同主题和路径验证 `presentation.create` 的复用性。
2. 在受控本机目录通过系统权限流程实际生成 `.pptx`，独立解析确认文件可读、幻灯片数与内容匹配；无权限时不落盘；仅 dry-run 通过不得报成功。经用户同意后再对桌面目标做真实验收，不把测试文件悄悄写到桌面。
3. 两个零宿主操作的历史追问任务不再被误判为“已执行宿主操作不可重放”；关联父任务后可解释准确错误。明确请求修复时进入 RepairJob，不以一次无证据的回答重写结束。
4. 系统源码修复在基线有红色复现、候选有绿色复现及全量测试后才可申请补丁批准；用户拒绝补丁或重启分别不应用或不激活新版本。候选代码不能通过修改固定测试、篡改结果或生成脚本冒充成功。
5. 修改审批、重启审批、哈希冲突、服务健康失败、自动回退、断电/进程重启恢复和五轮修复上限都有测试；未知宿主副作用不自动重放。`REPAIRED` 只在部署后的原需求真实复验通过时出现。
6. 全量单元、集成、API、前端测试与构建通过；实际 Ollama 加本机文件/审批链有一条可重复的端到端验收记录。不能运行的 Windows 桌面或隔离专项测试明确列为未验收，不以模拟结果替代。

## 9. 实施范围与顺序

正式计划应先做基线回归与本次 PPT/追问缺陷修复，再建立独立 RepairJob、候选补丁执行器、测试与审批、监督部署、健康与原任务复验，最后接入 UI 和真实本机验收。前后两增量分别有可运行测试与清晰终态；不得在自修复基础设施尚未交付时宣称贾维斯已经能修改自身源码。当前目录不是 Git 仓库，设计文档不能在此处提交；不会为满足流程而擅自初始化或覆盖仓库。
